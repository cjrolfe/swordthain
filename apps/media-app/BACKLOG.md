# Swordthain Media App — Backlog

Deferred features, known limitations, and settled decisions that don't need re-litigating. Not a roadmap — just a place to look before assuming something is unbuilt, half-built, or still open.

## Deferred features

- **Adaptive HLS** — would let playback adapt to the viewer's actual bandwidth and device (starts faster, less buffering on mobile data or a weak connection) instead of always pulling the single full-resolution original. Currently progressive-only (presigned S3 GET, HTTP Range seeking). True adaptive-bitrate HLS needs a real transcoding pipeline (nothing like this exists in the codebase today — the only ffmpeg use is a single-frame thumbnail grab) plus CloudFront with signed cookies in front of the *media bucket* specifically, coexisting with the current presigned-URL access model. Confirmed large scope (Aug 2026 investigation): a new AWS service or compute job, a new auth model, a new frontend player dependency, and a backfill of the ~29 existing videos. Worth a dedicated planning pass on its own, not a quick follow-up.
- **Passkey/WebAuthn sign-in** — would mean faster, friendlier sign-in (no waiting on an email code every time) and is phishing-resistant compared to email-OTP. Deferred: Cognito's native passkey support requires enabling `allowedFirstAuthFactors.password = true` at the User Pool level to turn on choice-based auth at all — even though no password UI would ever be built or shown to users. That conflicts with "no password path," a design principle stated twice in `infra/README.md`. The custom-OTP and passkey flows *can* technically coexist (confirmed via CDK's `ExplicitAuthFlows` — `ALLOW_CUSTOM_AUTH` and `ALLOW_USER_AUTH` are independent), so this isn't an all-or-nothing migration — but enabling it means accepting that pool-level tradeoff, which needs a deliberate decision, not just more research.

## Infra hardening still deferred

- **WAF bot-control in front of `MediaHttpApi`** — in progress (23-24 Aug 2026). A new CloudFront distribution (`ApiDistribution`, `HttpOrigin` → `MediaHttpApi`, `CACHING_DISABLED`) + WAF ACL (same 3 free managed rule groups as the site's) is live and verified — traffic confirmed routing through it correctly (real browser sign-in, folder/playlist listing, uploads). Rolled out in stages to keep production risk low: distribution+WAF deployed additively, CSP widened to allow both URLs, then the frontend cut over (`apps/media-app/.env`'s `VITE_API_URL`). Last step still open: after a confidence window, remove the old raw `execute-api` URL from the CSP `connect-src` to tighten it back down. **Known, accepted gap**: the raw `execute-api` URL stays reachable forever underneath the WAF — API Gateway HTTP APIs (v2) have no resource-policy mechanism to block direct access, so a bot that already knows that URL bypasses the new WAF entirely. Truly closing this would need a secret header CloudFront injects, validated by every Lambda handler — a materially bigger, cross-cutting change, not taken on here. This is a personal family app, not a high-value public target; the new WAF still meaningfully protects the normal swordthain.com-fronted path.

## Known content issues

- **ProRes `.mov` exports play in Safari only** (found 17 Oct 2026) — a 12GB, 15-minute ProRes 422 export uploads and thumbnails fine now, but Chrome/Firefox can't decode ProRes, so the picture won't render there (same symptom as `Paris.mp4` below). Re-encode to H.264 before uploading (e.g. `ffmpeg -i in.mov -c:v libx264 -crf 20 -pix_fmt yuv420p -c:a aac -movflags +faststart out.mp4` — roughly 2–3GB for the same clip). Not something the app can fix on the fly.
- **`Paris.mp4` won't display in the browser** (found 12 Aug 2026) — encoded with the old MPEG-4 Part 2 codec (`mpeg4`/`mp4v`), which no browser's `<video>` element can decode. Audio plays fine (AAC track, supported); the picture never renders (`videoWidth`/`videoHeight` stay `0`). Confirmed via `ffprobe` against the real file. Scanned every other video in the library (28 of 29) the same way — all are `h264` and play normally; this is a one-off, not a systemic problem. Fix has to happen at the file level (the app can't transcode on the fly): re-export/re-encode to H.264 (e.g. QuickTime's "Export As" or HandBrake) and re-upload — not something to build a feature around for one file.

## Settled decisions (recorded, not open questions)

- **No Glacier/Deep Archive tiering.** Evaluated at ~2TB scale; the extra saving over what Intelligent-Tiering's automatic tiers already capture is small (~$15–18/month) relative to the multi-hour restore delay and new product surface it would need (restore-initiate endpoint, "warming up" UI state). Revisit only if the library grows into the tens of TB.
- **Direct S3 mount + auto-detect.** Would have meant true drag-and-drop bulk upload — drop files into a mounted bucket and have them show up, no CLI or web uploader needed. Investigated and rejected: `folderId`/`mediaId` are opaque server-minted UUIDs with no relationship to folder titles or filenames, so a mounted bucket would show UUID soup, and a raw file drop wouldn't get a `mediaId` at all (the thumbnail Lambda's key-pattern check would silently skip it — no DB record ever created). There's also no IAM credential mechanism today — the whole security model is short-lived presigned URLs behind Cognito login, and mounting S3 would mean a real long-lived AWS access key sitting on a home machine. Would need a redesigned key scheme, a reconciliation Lambda, and a new credential story. The CLI upload tool (`apps/media-app-cli`) already covers the actual bulk-import need without any of this — not worth pursuing.
- **Apple Photos upload** — already works on iPhone/iPad: the existing upload input's native OS picker (Safari's file input) browses the real Photos library, including iCloud Photos, with multi-select. No code change needed. Mac browser uploads can't reach the Photos library directly (Finder's Open panel doesn't browse it) — closing that gap would need an iCloud Shared Album import (unofficial public endpoint) or a Shortcuts-based share flow; not pursued since iPhone/iPad covers the actual need.

## Recently shipped

- **Move folders** (10 Aug 2026) — `PATCH /folders/{id}` with `parentFolderId`, reparent anywhere in the tree via a breadcrumb-style destination picker in `FolderBrowser.tsx`. Rejects self-move (400) and move-into-own-descendant (409).
- **Delete media** (11 Aug 2026) — single-item delete for any photo/video, plus select-and-bulk-delete for photos. Removes both S3 objects (original + thumbnail) and the DB row.
- **Media description** (11 Aug 2026) — short (140 char) Owner-set text shown instead of the filename on every viewing surface (grid, Lightbox, playlist list/player); Activity log, CSV export, and downloads still use the real filename.
- **CLI upload fix** (11 Aug 2026) — files between ~2GB and 5GB were failing outright (Node's `fetch()` can't reliably send a single in-memory buffer body over ~2GiB). Lowered the CLI's multipart threshold to 1.9GiB so they route through the existing chunked upload instead.
- **CSP fix for browser uploads** (11 Aug 2026) — `connect-src` was missing the media S3 bucket, silently breaking every browser-initiated upload (any size) with a CSP-blocked "network error" — `img-src`/`media-src` covered viewing but not the XHR/fetch PUT calls uploads make directly to S3.
- **"Shared with me" list** (12 Aug 2026) — a folder nested under an unshared parent (e.g. moved under a new year-folder via Move) was real but unreachable for the Member it was shared with: access cascades downward from a shared ancestor, never upward to reveal the path to a deeper share. New `GET /folders/shared-with-me` lists every folder explicitly shared with the caller, with ancestor titles for display context only. Caught live against a real share that had gone quietly unreachable.
- **Automated regression-test suite** (12 Aug 2026) — `infra/regression-tests`, no OTP required (a dedicated, Owner-privileged test account with a fixed code, narrowly special-cased in `create-auth-challenge.ts`). Runs automatically after every deploy via `.github/workflows/regression-test.yml`; catches real gaps — its first live CI run correctly failed on a missing IAM grant the suite needed for its own test fixture, fixed the same day.
- **Friend-view clarity fixes** (12 Aug 2026) — clearer "add to playlist" picker wording for non-technical invitees, a larger/bolder media caption (was 12px at every screen width below 1600px), and a `visibilitychange`/`focus` listener so an already-open folder view picks up an Owner's description edit without a manual reload.
- **WCAG 2.1 AA conformance for `apps/media-app`** (12 Aug 2026) — heading hierarchy, table row headers, `aria-current` on tab nav, labels/`aria-label`s on previously-unlabeled inputs and icon-only controls, `role="status"`/`role="alert"` live regions, and color-contrast fixes across the app (base buttons, links, error/success text, the idle-warning banner, the Architecture legend, and — caught only once the automated suite below could actually run a real scan — the Lightbox/PlaylistPlayer dialogs' near-invisible text on their dark backdrop, and near-white text on white form inputs in the Member theme's light color-scheme). `Lightbox`/`PlaylistPlayer` also gained a real modal focus trap (`components/Dialog.tsx`): `role="dialog"`, focus-on-open, Tab trapped inside, focus restored to the trigger on Escape/close.
- **Automated accessibility test suite** (12 Aug 2026) — `infra/a11y-tests`, Playwright + axe-core against every Owner/Member tab and several interactive states (including an explicit keyboard Tab-cycling check for the modal focus trap, since axe only checks static ARIA, not runtime focus behavior). Same fixed-OTP sign-in as the regression suite; runs automatically after every deploy via `.github/workflows/a11y-test.yml`. `apps/playground`/`labs.swordthain.com` is a deferred follow-up, not covered yet.
- **Fullscreen video button fix** (12 Aug 2026) — the CloudFront `Permissions-Policy` header set `fullscreen=()` alongside the camera/microphone/geolocation lockdown, disabling the Fullscreen API for the site itself (not just third parties) and greying out the native `<video>` fullscreen control. Scoped to `fullscreen=(self)`.
- **`infra/a11y-tests` CI flake fix** (13 Aug 2026) — `PlaylistPlayer`'s WCAG scan test occasionally took 10-15s instead of ~2-5s, once hitting the full 90s CI budget. Root-caused via Playwright trace inspection (`--trace on`, then diffing action timings) to `axe-core`'s own `runPartial()` scan having real, externally-caused runtime variance unrelated to page/video state — mitigated with a generous, evidence-based 180s timeout plus CI failure-artifact capture (trace/screenshot/video on failure, `.github/workflows/a11y-test.yml`) for any future recurrence. Along the way, found and fixed a real, separate bug in the test's own self-healing cleanup sweep: `Locator.count()` doesn't auto-wait the way `.click()`/`expect()` do, so checking it immediately after a tab switch raced the playlist list's async load and silently left orphaned throwaway playlists behind; took three attempts to get right (documented in `infra/a11y-tests/README.md`). **Recurred 8 Sep 2026** — same test exceeded even the 180s timeout once in CI, unrelated to that day's actual change (confirmed: the failing test's own session-seeding path does zero extra work from that change, and a bare rerun of the same commit passed cleanly in 1m32s). Left as a known, still-not-fully-resolved flake rather than chased further at the time — worth a dedicated look if it keeps recurring.
- **`light-dark()` fallback for older browsers** (14 Aug 2026) — found live on an LG WebOS smart-TV browser: unreadable text/missing backgrounds app-wide (login card, form inputs, links, badges, etc.). Root cause: `apps/media-app/src/styles.css` uses the CSS `light-dark()` function extensively (added throughout the 12 Aug WCAG work); TV browsers often run an older engine that doesn't support it, and an unsupported CSS value drops the *entire* declaration — leaving color/background at their inherited/initial defaults instead of either theme's colors. Fixed by declaring a plain fallback value immediately before every `light-dark(...)` declaration (the standard progressive-enhancement pattern for this function): browsers that support `light-dark()` still apply it normally (declared second, wins the cascade); ones that don't just keep the fallback instead of falling through to nothing. Re-verified the full WCAG 2.1 AA suite afterward — zero violations.
- **Playlist orphaned-item cascade cleanup** (17 Aug 2026) — deleting a media item now removes any `PlaylistItems` rows referencing it, across every playlist that has it (new `byMedia` GSI on `PlaylistItemsTable`, queried by `deleteMedia`), and decrements each affected playlist's `itemCount` correctly. Previously the row was only ever tolerated as an advisory `available: false` at read time, accumulating forever. Going forward only — any orphans that may already exist from the 11–17 Aug window weren't backfilled, since they're already tolerated the same way today.
- **`robots.txt`** (23 Aug 2026) — `apps/media-app/public/robots.txt` (`Disallow: /`), matching the existing `noindex, nofollow` meta tag. Vite copies `public/` to `dist/`'s root untouched; no deploy workflow changes needed.
- **Splash intro + admin kill switch** (8 Sep 2026) — a one-time "studio ident" splash (`Splash.tsx`) plays right after sign-in: a broadsword push-in video (AI-generated, Artlist) with a real HTML "Swordthain" wordmark stamped over the crossguard and a cinematic music sting, muxed together. Click-to-enter, since sound can't reliably autoplay without a prior user gesture — same trick the Lightbox's own `<video>` already relies on. Shown once per browser ever (`localStorage`), skipped entirely for `prefers-reduced-motion`, always skippable (Skip button, Escape). New Owner-only **Settings** tab holds a global on/off toggle backed by a new `AppSettingsTable` + `settings.ts` Lambda (`GET /settings` readable by any signed-in user, `PATCH /settings` Owner-only) — the reason the splash plays after sign-in rather than before Login: checking a server-side setting needs a real session, and this API has no unauthenticated routes. **Known gap**: no Member test account exists in `infra/regression-tests`, so the PATCH-as-Member-should-403 case is covered by code review of `settings.ts`'s `isOwner()` check, not an automated test.
- **Large-upload fixes** (17 Oct 2026) — a 12GB web upload got all 230 parts into S3, then failed on the final `complete` call: the WAF added in August blocks request bodies over 8KB, and listing every part (~66 bytes each) put this one at 15KB — so any web upload over roughly 6GB would have failed at the very last step. `POST /media/upload-url/multipart/complete` now takes just `totalParts` and the server asks S3 which parts arrived, refusing (409) if any are missing so it can't finalize a truncated file; the old `parts` list is still accepted for the CLI. Same file would also have hit a second limit even once uploaded: `ThumbnailFn` downloaded the whole video into Lambda's 10GiB `/tmp` before grabbing one frame, so it never would have gotten a library entry. It now reads straight from S3 over a presigned URL (one frame from a real 3.5GB video in 0.37s), with the download kept as a fallback. New `multipart` regression scenario covers both.
